# 从书签导入模板 URL 设计

## 背景

现有模板 URL 页面已经支持手动创建、编辑、删除和执行模板，但仍然需要用户自己从零编写 URL 模板。

本次需求是在模板 URL 页面新增“从当前书签导入”的能力，允许用户选择一个书签文件夹，读取其中一批书签 URL，自动识别结构相似的书签组，并生成可确认导入的模板候选。

目标场景包括 Kibana、日志检索、运营后台筛选页等“URL 结构基本一致、但局部参数不同”的书签集合。

## 目标

- 在模板 URL 页面新增“从书签导入”入口
- 支持按书签文件夹读取一批书签
- 自动聚类结构相似的书签 URL
- 识别可抽象成变量的差异位
- 生成候选模板列表，允许用户逐个导入
- 支持“编辑后导入”，复用现有模板编辑弹窗

## 非目标

- 不支持手动多选零散书签导入
- 不支持自动批量无确认导入
- 不支持一键全选导入所有候选
- 不做高级语义理解或业务字段推断
- 不做历史记录、推荐变量名学习、导入规则配置
- 不把导入逻辑扩展到 Dock 或普通书签管理页面

## 用户确认范围

本次已确认的范围如下：

- 入口形式：模板 URL 页面中的“从书签导入”按钮
- 导入来源：选择一个书签文件夹，读取其下全部书签
- 候选处理：生成候选模板列表，逐个确认导入
- 变量识别：保守策略，只抽结构相同位置上的差异值
- 默认命名：使用“文件夹名 + 域名”
- 不使用可视化浏览器辅助，文本设计足够

## 现状约束

当前模板 URL 页面已经具备：

- 模板列表页
- 新增/编辑模板弹窗
- 执行模板弹窗
- 本地存储与占位符解析逻辑

当前仓库已经具备：

- 书签树读取能力
- 文件夹选择组件
- 模板 URL 编辑能力
- `lib` 层测试组织方式

这意味着本次更适合做“导入候选生成 + 与现有编辑流程衔接”，而不是重做模板管理主流程。

## 核心方案

采用“导入弹窗 + 候选列表 + 单个确认导入”的方案。

流程如下：

1. 用户在模板 URL 页面点击 `从书签导入`
2. 打开导入弹窗，选择一个书签文件夹
3. 点击 `扫描书签`
4. 系统读取该文件夹中的全部书签 URL
5. 对书签进行结构相似聚类与变量识别
6. 展示候选模板列表
7. 用户可对每个候选执行：
   - `导入`
   - `编辑后导入`

采用这个方案的原因：

- 风险可控，不会直接把误判模板写入模板库
- 能和现有页面结构自然融合
- 复用现有模板编辑弹窗，减少重复 UI
- 更适合首版算法仍在保守模式下迭代

## 页面交互设计

### 模板 URL 页面

在现有顶部操作区增加一个次级按钮：

- `从书签导入`

保留现有 `新增模板` 按钮，两者并列展示。

点击 `从书签导入` 后，打开导入弹窗，不离开当前页面。

### 导入弹窗

导入弹窗分三个状态：

#### 1. 选择文件夹

展示：

- 文件夹选择器
- 简短说明文案
- `扫描书签` 按钮

规则：

- 必须先选择文件夹
- 如果所选文件夹没有书签或书签数量不足，扫描后显示空状态

#### 2. 扫描中

展示：

- 加载状态
- 当前说明文案

规则：

- 禁止重复提交
- 不允许在扫描中再次切换文件夹

#### 3. 候选模板列表

展示候选模板卡片列表，每个候选卡片包含：

- 默认模板名
- 来源域名
- 样本数量
- 生成后的模板 URL
- 识别出的变量列表
- 1 到 2 条样本 URL 预览

每个候选项提供两个动作：

- `导入`
- `编辑后导入`

#### `导入`

直接按当前候选的默认数据写入模板库。

#### `编辑后导入`

打开现有模板编辑弹窗，预填：

- 模板名称
- 模板说明（可选）
- 模板 URL
- 默认打开方式

用户修改后再保存。

## 文件夹选择组件策略

导入时文件夹可能较多，且用户往往知道想导入的大致目录名称，因此推荐复用可搜索的文件夹选择器，而不是级联型组件。

优先复用：

- `components/ui/searchable-folder-select.tsx`

原因：

- 搜索大量目录时效率更高
- 和“按文件夹导入一批书签”的任务更匹配
- 交互负担比层层展开更小

## 候选模板数据结构

建议新增候选数据结构：

```ts
interface ImportedTemplateCandidate {
    id: string;
    name: string;
    domain: string;
    sampleCount: number;
    urlTemplate: string;
    placeholders: string[];
    sampleUrls: string[];
    sourceBookmarkIds: string[];
}
```

说明：

- `id` 仅用于候选渲染，不写入最终模板库
- `name` 是默认模板名，可在编辑后导入时修改
- `sampleUrls` 只保留少量样本用于展示
- `sourceBookmarkIds` 用于后续可能的追踪、调试或去重扩展

## 默认命名策略

默认模板名称采用：

- `文件夹名 + 域名`

例如：

- `支付监控 · shop-elk.tuhuyun.cn`

不强制从书签标题提取公共前缀。

原因：

- 标题风格不稳定时更稳
- Kibana、日志后台等场景通常文件夹名更有组织语义
- 实现简单，误判少

## 聚类与变量识别设计

### 总体策略

采用“结构相似聚类 + 差异位替换”的保守策略，不做业务语义解析。

首版明确只在 URL 文本层面做结构比较与变量替换，不解析 Kibana 或其他系统的内部 DSL 语法树。

### 第一步：按域名和路径预分组

先把书签按以下维度分桶：

- `protocol + host`
- 主路径
- hash 中的主路径骨架

例如：

- `https://shop-elk.tuhuyun.cn/app/kibana#/discover`

只有落在相同入口骨架上的书签，才进入下一步结构比较。

### 第二步：结构相似性比较

在同一分组内部，进一步比较：

- query 参数 key 集合是否一致
- hash 片段中的主骨架是否一致
- 特殊分隔符、括号、层级结构是否整体一致
- 大段字符串在局部替换后能否保持相同骨架

只有结构足够相似，才合并为同一个候选模板。

### 第三步：变量位识别

对于结构相似的一组 URL，识别“相同上下文中取值不同”的片段，并替换成占位符。

规则：

- 必须是同一位置上的差异
- 差异值前后固定上下文必须稳定
- 替换后整体 URL 仍需合法

例如可识别的变量位包括：

- `applicationName` 对应值
- 时间范围中的 `from`
- 时间范围中的 `to`

但首版不要求真正理解它们的业务语义。

### 变量命名策略

默认优先采用保守命名：

- `var1`
- `var2`
- `var3`

允许一个有限增强：

如果某个变量位附近存在稳定、明确的文本 key，例如：

- `applicationName:`
- `from:`
- `to:`

则可以生成更可读的默认名，例如：

- `applicationName`
- `timeFrom`
- `timeTo`

但这不是首版强制要求。首版的核心目标是识别位置正确，而不是变量名足够聪明。

### 生成候选的门槛

只有满足以下条件才生成候选模板：

- 至少 2 个书签样本
- 至少识别出 1 个变量位
- 生成后的模板 URL 仍然合法

以下情况不生成候选：

- 书签只有 1 条
- 结构差异过大
- 替换变量后 URL 无法通过校验

## 导入行为设计

### 直接导入

点击 `导入` 时：

1. 将候选模板转换为 `SaveTemplateUrlInput`
2. 使用现有模板存储逻辑保存
3. 成功后刷新模板列表
4. 候选项标记为已导入或从列表移除

建议首版采用“导入成功后从候选列表移除”的策略，减少重复导入。

### 编辑后导入

点击 `编辑后导入` 时：

1. 将候选模板数据映射为模板表单初始值
2. 关闭或挂起导入弹窗当前候选交互
3. 打开现有模板编辑弹窗
4. 用户保存后，刷新模板列表

建议交互策略：

- 保留导入弹窗的候选上下文
- 编辑完成后回到候选列表

这样用户可以连续处理多个候选，而不需要每次重新扫描。

  - 文件夹选择
  - 触发扫描
  - 渲染候选列表

- `template-url-import-candidate-card.tsx`：
  - 单个候选项展示
  - 导入、编辑后导入按钮

### 新逻辑模块

- `lib/templateUrlImportUtils.ts`

职责：

- 将一批书签 URL 聚类成候选模板

- 生成模板候选结构

不建议把这部分逻辑直接写进 `bookmarkUtils.ts`，以避免职责污染。

## 与现有模板编辑弹窗的衔接

现有模板编辑弹窗已经支持：

- 模板名称
- 模板描述
- URL 模板
- 占位符解析
- 默认打开方式

因此编辑后导入时，只需要提供预填初始值，不需要重新实现确认表单。

设计要求：

- 导入候选与现有编辑弹窗使用同一套模板保存流程
- 不新增另一套专门的“导入后编辑表单”

## 错误处理策略

### 文件夹为空或书签不足

在导入弹窗内显示空状态，不使用 destructive toast。

提示内容包括：

- 当前文件夹没有可用于聚类的书签
- 需要至少 2 条结构相似的书签才能生成候选

### 扫描失败

适用场景：

- 读取书签失败
- 聚类算法抛错
- URL 预处理异常

处理方式：

- toast 提示错误
- 弹窗内显示简短错误说明
- 允许用户重新选择文件夹并重试

### 单个候选导入失败

处理方式：

- 只标记该候选项失败
- 不关闭整个弹窗
- 其他候选仍可继续操作

## 主题与视觉要求

必须保持与现有模板 URL 页面和全局主题系统一致。

要求：

- 使用现有 `Card`、`Button`、`Dialog`、`Badge`、`Select` 风格
- 兼容默认主题与 `blueprint` 主题
- 不新增与当前视觉语言冲突的表单样式
- 候选卡片应沿用现有模板卡片的表面、描边、圆角与文字层级

## 测试策略

首版仍然只测试 `lib` 层。

新增：

- `lib/__tests__/templateUrlImportUtils.test.ts`

覆盖点包括：

- 按域名和路径预分组
- 结构相似 URL 能聚成同一候选
- 同一位置差异会生成变量位
- 少于 2 条样本时不生成候选
- 结构差异过大时不会误合并
- 生成后的模板 URL 保持合法

不新增 UI 测试，保持与当前仓库测试风格一致。

## 验收标准

满足以下条件视为本次功能完成：

- 模板 URL 页面出现 `从书签导入` 按钮
- 用户可以选择一个书签文件夹并扫描
- 系统能从一批结构相似的书签生成候选模板
- 候选模板会展示模板 URL、变量和样本数量
- 用户可以对单个候选执行 `导入`
- 用户可以对单个候选执行 `编辑后导入`
- 导入后的模板出现在现有模板列表中
- 导入界面与现有主题系统保持一致
- `lib` 层导入算法测试覆盖核心分组和变量识别逻辑

## 风险与注意事项

- Kibana 这类 URL 中包含大量嵌套 DSL 结构，若算法过于激进，容易误把结构性片段抽成变量
- 首版不解析 Kibana DSL 语法树，因此变量识别的精度取决于文本骨架匹配策略，必须接受“偏保守、少识别，不误识别”的取舍
- 某些书签 URL 可能包含不可见字符或复制污染字符，预处理时需要清洗
- 如果候选生成策略过于宽松，会把不同查询入口错误合并；首版应偏保守
- 编辑后导入的流程必须复用现有模板弹窗，避免出现两套保存逻辑

## 实施边界

本次实现只应包含：

- 模板 URL 页面导入入口
- 文件夹选择与扫描弹窗
- 候选模板展示
- 单个候选导入与编辑后导入
- 导入算法与对应测试

本次不应扩展到：

- 手动多选书签导入
- 批量全选导入
- 自动无确认导入
- 导入规则可配置化
- 高级语义识别
- Dock 联动
